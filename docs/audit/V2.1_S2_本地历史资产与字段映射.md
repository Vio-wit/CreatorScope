## E. 数据库兼容性与后续隔离演练建议

当前 SQLite v3 的 `creators`、`notes`、`records`、`metric_values`、`batches` 和 `collection_field_observations` 可表达部分实体、来源、批次、指标原值及观察状态，但尚不构成通用历史证据模型。`records.fields_json` 可存来源字段，指标的单位、周期以及时间必须独立核查；列表/详情的捕获状态不自动证明语义正确。

当前 `ensure_creator_ref` 优先来源引用，再尝试平台和公开 ID，且会更新已有 `creator_name`、`platform_creator_id`；`ingest_payload` 的覆盖路径也可更新这些字段。因此它不应直接作为 V2.1 历史导入的冲突处理规则。现有 `historical_import.py` 面向特定 JSON/JSONL，并存在缺少采集时间时回退到本地当前时间的逻辑；未知历史采集时间不能因此被视作真实时间。上述代码均未运行。

后续 S3/S4 可按以下顺序实施并测试：

1. 在单独的隔离 SQLite 中保留来源文件指纹、路径、行号、源字段和值、真实可证时间及映射版本；重复文件识别后保留各来源引用。
2. 将平台、标识类型和标识值分开保存。相同平台、相同类型的强标识一致时关联；明确冲突禁止合并；无 ID 的名称及来源记录保留为待核验，文本差异保留别名，不覆盖已核验身份。
3. 在证据层追加可解析数值、单位、统计周期和失败/缺失状态；映射失败或字段不兼容时保留原文，不因为非核心字段缺失拒绝整条记录。
4. 做幂等重导、同名不同 ID、相同 ID 别名、缺 ID、冲突、`--`、0 与空值、单位/周期不兼容等隔离测试，并核对行数、来源、恢复流程和图表的有效样本数。
5. 正式库若需修改，先明确具体变更、备份并验证恢复方案；当前阶段未修改正式数据库，也未建立统一分析数据集或扩展看板。
